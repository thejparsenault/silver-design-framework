Silver 0.6.0 — Agent Hosts and Guarded Invocation

This is the first public release. It responds to an audit of 0.5 against Claude
Code and Claude Cowork, recorded in `docs/silver-0.5-audit.md`.

## Install

No npm account, login, or registry token is needed. npm accepts a remote tarball
as a package spec, so the release asset below runs anonymously:

```sh
npx --yes https://github.com/thejparsenault/silver-design-framework/releases/download/v0.6.0/silver-design-framework-0.6.0.tgz setup inspect . --json
```

Requires Node.js 20.11 or newer. Silver checks and tells you how to install it
rather than failing obscurely.

Do not run `npx silver`. An unrelated package holds that name on npm.

## An installed workspace can now run its own skills

Setup copied the runtime into `.silver/runtime/`, but that code imports `ajv`,
`ajv-formats`, and `yaml` as bare specifiers that do not resolve in a workspace
outside a `node_modules` tree. Every guarded invocation failed with
`ERR_MODULE_NOT_FOUND` on the documented install path, for all twenty-one skills
and the `what-now` analyzer.

Execution routes through the CLI, which always runs where its dependencies
resolve. Setup generates `.silver/bin/silver` so a workspace has one stable
command regardless of how the CLI was delivered.

## Claude Code discovery

Claude Code reads `CLAUDE.md` rather than `AGENTS.md` and finds skills only
under `.claude/skills/`, so a Silver workspace was invisible to it. Setup now
generates a `CLAUDE.md` that imports `@AGENTS.md`, `.claude/skills/<id>`
symlinks into the canonical `.skills/`, and `allowed-tools` frontmatter on every
skill. `.skills/` and `AGENTS.md` stay canonical; the adapters are generated,
repairable, and safe to delete.

Claude Cowork is not supported. It loads only account-level skills and runs code
in an isolated remote environment, so it needs a durable-output path that does
not require Node. See `docs/agent-host-compatibility.md`.

## Guarded invocation is scaffolded

`silver invoke --scaffold <skill-id>` emits a schema-valid request prefilled with
identifiers, timestamps, the provenance envelope, the active design-context pin,
required checks, and `expected_integrity` for any file being replaced. You supply
content and reasons. Placeholders carry a sentinel and `silver invoke` refuses a
request that still contains one.

## The documented install path works

Three failures made it unusable, the worst a loop: a plan file written inside the
inspected directory changed that directory and invalidated itself, and
re-inspecting invalidated again. `setup apply` now accepts `-` and reads the plan
from stdin:

```sh
silver setup inspect . --json                      # review this
silver setup inspect . --answers '{"team_shape":"solo","topology":"integrated"}' --json \
  | silver setup apply -
```

`--answers` accepts inline JSON. `team_shape` and `topology` must be answered
before apply, so a human confirms the repository topology rather than the agent
guessing.
