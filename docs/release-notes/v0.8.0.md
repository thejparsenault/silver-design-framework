Silver 0.8.0 — Tools That Are Actually There

Your preferred tool gets used when it is there. When it is not, you are told
which one, why, and what you can do about it — instead of having a substitute
picked for you.

## Install

```sh
npx --yes silver-design-framework@0.8.0 setup inspect . --json
```

Requires Node.js 20.11 or newer. Do not run `npx silver`; an unrelated package
holds that name.

Existing workspaces upgrade with a reviewable migration:

```sh
.silver/bin/silver migrate .            # preview
.silver/bin/silver migrate . --apply
```

## Why this release exists

0.7 made the runtime honest about checks. The tool layer was still a stub.

The vocabulary was complete — capabilities, actions, providers, degraded
coverage, all enforced. Nothing chose between them. `resolveCapabilities` picked
a provider by **alphabetical first-wins** and ignored even the skill's own
preference hints. `selectProvider` implemented ordered preference and had zero
callers. The tool-profile contract had a `priority` field nothing read from disk.
And the only external provider reported itself permanently unavailable, so there
was nothing to choose between anyway.

"Figma" was also the wrong unit. What you pick is a *transport*, and the
transports to one tool are good at different jobs.

## Activities: naming the work

An activity is a human-named unit of tool-using design work — "build flows in a
design tool", "push design-system updates to a design tool". It names a
capability, the actions taken with it, and sometimes the artifact kinds
involved, which is what separates pushing a token source from pushing a flow
when both are `(design-file, write)`.

Which providers and skills serve an activity is **derived** from their existing
contracts. Nothing declares it twice, and a contract check fails the build in
both directions — a `served` activity with no provider, and a `planned` one that
a shipped provider now covers.

## Transports: Figma is not one thing

`figma` becomes `figma-console-mcp` and `figma-official-mcp`. They declare
different `directions` and different artifact kinds, so the read-oriented one is
never a candidate for a push, and you can bind pulling and pushing to different
transports in the same workspace.

Each declares a **setup ladder** of typed steps — installed in another app, run
in a terminal, a background process, or Silver-managed — with each step saying
who can verify it. So `doctor` tells you "the plugin is installed, the server is
not running" instead of "figma-pilot unavailable".

## One order, two filters, and a question

Order runs personal → project → team → framework default. The first source that
binds an activity wins outright; sources are not merged.

Two filters always apply. **Availability**, per the ladder. And **veto** — a
project, team, organization, or machine policy may forbid a transport, and no
preference overrides it. A team can say "no remote transports for our design
files"; a team cannot dictate which client runs on your laptop.

**Your chain is an offer list, not an auto-fallback list.** When your preferred
transport is unavailable, Silver reports why and asks — wait while you fix it,
use the next one, or stop. Set `on_unavailable: use_next` if you would rather it
just moved on. Where nobody can be asked, at a script or a non-TTY shell, the run
stops with a resumable request rather than choosing while you are not looking.

## Nothing is removed silently

This is now a framework constraint, not just behaviour. Every transport removed
from the running is recorded with its reason, its source when vetoed, the setup
step that failed when unavailable, and **who can lift it** — you, the project
owner, or a policy owner. A vetoed transport and a broken one look identical
unless the difference is stated, and you cannot act on what you cannot see.

New: `silver tools` shows, per activity, what will be used, which source ordered
it, everything that was removed and why, and what would work if it were set up.

## Declaring tools, never installing them

The line is ownership, not difficulty:

| Silver does | Silver does not |
| --- | --- |
| Detect what is present | Install software |
| Write your host's MCP declaration for an installed tool, on `--connect` | Clone or build a repository |
| Name required environment variables | Read or store a credential |
| Print the exact commands | Run them |

`silver tools --connect <transport>` writes the declaration into `.mcp.json` and
prints what remains yours to do. It never writes a credential, and it refuses to
rewrite a host config that already holds one. Where Silver does not know how a
server is launched, it says so and hands back the steps rather than guessing a
command into your agent configuration.

Silver has **no network transport layer at all**. When a transport is an MCP
server, your agent host owns the connection, the authorization, and the process.
Silver never opens a socket. It follows that Silver can only establish that a
transport is *configured*, never that it *responds* — so it verifies the
artifacts that came back, not the transport that claimed to produce them.

## Silver only knows what it ships and what you tell it

There is no web search for tools and no agent-proposed tool. Recommending a
repository found by search would launder an unvetted project into an
endorsement, and refusing to install it is not protection when the
recommendation is what sends you to install it yourself.

Instead: an MCP server in your host that no shipped adapter claims is reported
as **unmapped**. Silver knows it exists and nothing more, so it asks what it is
for and never uses it until you answer. When nothing can serve an activity,
Silver names the transports it ships that could, and prints their ladders.

The honest cost: if you do not already know a tool exists, you will not learn it
here.

## Fixes

- Changing your studio voice through `silver practice apply` now works. It wrote
  prose into `PRACTICE.md`, which the resolver never reads — validating,
  committing, reporting success, and doing nothing.
- Skills declare effects for their optional capabilities, so what a skill does
  with a design tool is stated rather than assumed.
- Duplicate effect declarations removed from the `system` and `prototype`
  contracts.
- `copyNewTree` on a missing source no longer aborts an update partway through.

## Compatibility

Skill contracts, providers, the guardrail registry, and the default playbook move
to `0.8.0`. New: `silver/activity-catalog/v1` and `silver/tool-preferences/v1`.
`silver/provider/v1` gains `target`, `variant`, `aliases`, `connection`,
`requires_env`, and `setup`. `silver/skill-result/v2` gains `transports` and a
per-provider `activity`. The manifest gains `tool_preferences`. The lock gains an
`activity-catalog` package type.

`tool-profile/v2` is superseded by `tool-preferences/v1` and stays readable for
compatibility, like the permission layer.

Migration removes the retired `figma` provider package and installs the
transports and activity catalog. A 0.6.1 workspace migrates with zero conflicts,
zero doctor diagnostics, and its checks passing.

`npm run build` passes 113 tests; `npm run test:package` passes for the exact
release archive.
