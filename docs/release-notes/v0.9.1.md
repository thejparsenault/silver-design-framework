# Silver 0.9.1 — Paths, Tools, and Honest Fallbacks

A patch release. It fixes a contract path that blocked one skill outright,
gives skills the file tools their own documented workflow requires, and makes
the framework's fallback machinery either work or say plainly that it does not.

## Fixes

- **`theme` can write tokens again.** 0.9.0 moved the canonical layout to
  `design/system/`, but the `theme` contract still declared its `token-source`
  output at the retired `reference-system/tokens/**`. Every invocation that
  wrote tokens where they actually live was refused before it changed anything:
  `Skill theme cannot produce token-source at design/system/tokens/…`. The
  retired path is gone from all 25 skill contracts, and a contract test now
  fails if it returns.

- **Skills can edit files.** All 25 skills declared two Bash patterns and
  nothing else, which left the documented scaffold → fill in → invoke workflow
  with no legal tool for its middle step. They now declare `Read`, `Write`,
  `Edit`, `Glob`, and `Grep`. What an invocation may actually touch is still
  decided by its declared effects, path scoping, integrity fingerprints, and the
  Git checkpoint preflight — not by withholding file tools.

- **The browser checks have a command.** `accessibility`,
  `responsive-behavior`, and `critical-interactions` are only produced by the
  browser suite, and the one documented way to run it was a `node .skills/…`
  command the skill's own tool list forbade. Use `silver check --browser`
  (optionally `--chrome <path>`). Windows Chrome locations are now discovered
  too; a Windows host previously found no browser at all unless
  `SILVER_CHROME_PATH` was set.

- **A cloned workspace explains itself.** A Silver workspace is a Git
  repository and `node_modules/` is not committed, so cloning one onto a machine
  without Silver or Node.js is ordinary. It used to fail with
  `exec: npx: not found` — naming neither Silver nor anywhere to get it. The
  launcher now says what is missing and points at both the macOS package and the
  npm command.

- **One copied script could never run.** `what-now`'s workspace analysis
  imported `yaml`, which a workspace cannot resolve — Silver bundles its
  dependencies inside its own package, and Node's resolver only searches upward,
  never into a sibling package's private files. It now uses the dependency-free
  reader the design checks already use.

- **The runtime mirror can find the payload.** `.silver/runtime/` is a copy of
  the guarded runtime kept beside every workspace. Since 0.9.0 introduced the
  native distribution it had been unable to locate the schemas, guardrails,
  activities, providers, and transports sitting next to it. It resolves them
  correctly again. It still cannot execute for want of its npm dependencies, and
  the comments that claimed otherwise now say so: read `.silver/runtime/` as
  inspectable, integrity-checked evidence of the rules being enforced, not as a
  working fallback. The CLI is the engine.

## Upgrading

`silver update .` previews the change and makes no modifications until you
approve it. Framework-managed files are replaced; anything copied-and-owned,
including your `design/system/tokens/` seed, is only ever proposed.

One behavioral change is worth knowing before you update: the widened skill
tool declarations take effect in an existing workspace as soon as its `.skills/`
files are updated. An agent that previously could only invoke the Silver CLI
will also be able to read and write project files directly.

## Install

Unchanged from 0.9.0 — the macOS packages, a project or global npm install, a
one-off `npx` run, or the GitHub release archive. See the
[README](../../README.md) for all of them and
[Silver 0.9 acceptance criteria](../silver-0.9-acceptance.md) for the release
boundary.
